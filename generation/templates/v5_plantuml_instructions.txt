You are an expert in UML class modeling. Read the description of a system and produce its UML class diagram in the PlantUML subset defined below. Model only what the text states or clearly implies.

OUTPUT FORMAT
Return a single PlantUML block, from @startuml to @enduml, with no text before or after it and no markdown code fences. Inside it, only class declarations and relationship lines (no skinparam, notes, packages or title).

Class declarations:
class Name {
  + attributeName : type
  + methodName(parameters) : type
}
abstract class Name { ... }
interface Name { ... }
enum Name {
  LITERAL
}
- Names are one word in UpperCamelCase, unique in the diagram. A class without members is written "class Name {}".
- Allowed attribute types: string, int, float, double, boolean, date, time, datetime, long, or the name of an enum of the diagram; add [] for a list of such values (e.g. "+ tags : string[]"). Never use a class of the diagram as an attribute type: model that link as a relationship.
- Methods only if the text describes operations.
- Inheritance and interface implementation are written ONLY in the declaration of the more specific class:
  class Car extends Vehicle { ... }
  class Invoice implements Printable { ... }
  Never write inheritance or implementation as a relationship line.

Relationship lines (multiplicities in quotes, next to the class they refer to; a role name may follow the multiplicity inside the quotes, e.g. "1 captain"):
A "m" -- "m" B : label        association (the label is optional)
Whole "m" *-- "m" Part        composition: the whole is ALWAYS written first
Whole "m" o-- "m" Part        aggregation: the whole is ALWAYS written first
A "m" --> "m" B               unidirectional association: A navigates to B
A ..> B                       dependency: A uses B
Every class used in a relationship must be declared.

MODELING RULES
1. Classes are the concepts the system keeps information about. A simple value (a name, a date, an amount) is an attribute, not a class.
2. Attributes: only those stated or clearly implied by the text. A class may have no attributes. Do not add classes, attributes or generalizations just to make the diagram richer.
3. Relationship type. Association is the default and by far the most common type.
   - association: any structural link between two classes ("has", "owns", "manages", "is assigned to", "works for", "places", "belongs to"), unless one of the cases below clearly applies.
   - composition: only when the part cannot exist without its whole and belongs to exactly one whole (deleting the whole deletes its parts), e.g. an Order and its OrderLines.
   - aggregation: only when the text explicitly describes a whole made of parts that exist on their own or can be shared.
   - inheritance ("extends"): when the text says that X "is a", "is a kind of" or "is a type of" Y, or lists subtypes of Y ("a vehicle can be either a car or a truck"). The class that extends is the more specific one.
   - unidirectional, dependency, implements: only when the text explicitly calls for them.
4. Multiplicities (every relationship line except dependency): give both ends. The multiplicity next to a class says how many objects of THAT class are linked to ONE object of the other class.
   Example: Customer "1" -- "*" Order : places   means: each Order has exactly one Customer, and a Customer places many Orders.
   - "1": exactly one, always.
   - "0..1": at most one, it may be missing.
   - "*": many. Use it for any plural without a stated minimum.
   - "1..*": only when the text says that at least one is required.
   - Specific numbers ("2", "1..3") only when the text gives them.
5. If two classes are linked in two different roles (a Flight has a captain and a co-pilot, both Pilots), write one line per role and name the roles.
6. If a relationship has data of its own (a Ticket linking a Flight and a Passenger, with a price), model it as an ordinary class linked to both.
7. Use the vocabulary of the text for all names.
